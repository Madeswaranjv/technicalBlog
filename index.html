Introduction

Veridic sits between an AI agent and an MCP server. Every tool call the agent emits — create_payment, send_email, query_database — passes through Veridic before any real API is touched. Veridic extracts entity claims from the call, checks them against its Ground-Truth Entity Index (GTEI), and returns one of three verdicts: ALLOW, BLOCK, or ESCALATE.

Designing Veridic created two structural tensions. First, we need multiple ways to score a claim — exact string match, fuzzy Levenshtein ratio, ML sentence-encoder — and we need to swap them without rewriting the policy layer that acts on the score. Second, not every call should reach the ML model: a cache hit should exit at step two, a schema error at step one.

The Bridge pattern resolves the first tension by decoupling how a score is computed from what policy is applied to it. The Chain of Responsibility resolves the second by letting each verification stage either claim a request or forward it, so requests exit as early as possible.

1 — Bridge Pattern

Intent

"Decouple an abstraction from its implementation so that the two can vary independently." — Gang of Four, Design Patterns: Elements of Reusable Object-Oriented Software, 1994

The Bridge pattern splits one class hierarchy into two. The Abstraction side defines high-level policy; the Implementor side provides the concrete mechanism. The Abstraction holds a reference to an Implementor interface — either side can be extended or replaced without touching the other.

Problem in Veridic

Before Bridge, Veridic had a single Verifier class with a Strategy enum and a large switch inside verify(). Adding a new scoring algorithm meant editing that class directly, touching its tests, and scheduling a deployment. Supporting both strict (financial) and lenient (content) policies on top of multiple algorithms required wrapping everything in conditional branches. The class grew until it was responsible for both what score to require and how to compute the score.

With three policies × three algorithms, a naive inheritance approach requires nine concrete subclasses. Bridge collapses this to three + three = six independently extensible classes.

Solution & Class Diagram

The Bridge seam falls between "which confidence threshold policy applies" (Abstraction) and "how a confidence score is computed" (Implementor). VerificationAbstraction holds a reference (bridge) to the IVerificationBridge interface. The two refined abstractions and three implementors are completely independent — any combination works.

2 — Chain of Responsibility


        
Intent

        

          "Avoid coupling the sender of a request to its receiver by giving more than one
          object a chance to handle the request. Chain the receiving objects and pass the
          request along the chain until an object handles it."
          — Gang of Four, Design Patterns: Elements of Reusable Object-Oriented Software, 1994
        

        

          Each handler either resolves the request and stops propagation, or calls its
          successor. The sender knows only the head of the chain — not which handler will
          ultimately respond.
        


        
Problem in Veridic

        

          Before Chain of Responsibility, Veridic's verification entry point was a single
          900-line method — schema check, cache lookup, exact match, fuzzy match, ML
          inference, default block — all inline. Adding a Redis cache check meant editing
          the ML path. Every call paid the full worst-case cost even when a schema error
          alone was enough to block the request.
        

        

          The real cost: the monolithic method always ran every stage. Calls that should
          have exited at the cache still reached the ML model. In production, 68% of
          calls are resolvable before the ML stage. The old design made all of them pay
          the full ~1.2 s ML latency anyway.
        


        
Solution & Class Diagram

        

          Veridic builds a six-handler chain ordered by cost. Each handler is one class
          with one job. setNext() returns its argument, so the
          entire chain is wired in a single fluent expression. Handlers are ignorant of
          each other — adding a new stage means one new class and one change to the
          chain builder.

Conclusion

        

          Bridge and Chain of Responsibility are not stylistic choices in Veridic —
          they are direct responses to structural forces in the problem domain. Bridge
          exists because we need to compose policies with algorithms without a
          combinatorial class explosion. Chain of Responsibility exists because
          verification is an ordered sequence of ever-more-expensive checks, and any
          request that can be resolved early should never pay the full cost.
        

        

          Reading the GoF intent statements carefully against a real problem points to
          the right pattern reliably. The intent of Bridge is exactly Veridic's first
          tension. The intent of Chain of Responsibility is exactly the second.
          Understanding why a pattern was chosen matters more than memorizing
          its structure — these two examples show why.
